EvidenceX — Product Requirements Document

"From Scattered Evidence to Structured Investigation."

Hackathon problem statement: Organizing Evidence After an Online Fraud Incident.

1. Problem & Vision

Victims and investigators end up with fraud evidence spread across screenshots, chats, bank alerts, emails, and URLs — no timeline, no way to spot contradictions, no way to prove where a "fact" came from. EvidenceX is an investigation-support tool that turns that mess into a structured, chronological, traceable incident record — without ever deciding guilt, fixing conflicts on the user's behalf, or inventing facts that aren't in the evidence.

Non-goals (explicit): no guilt determination, no auto-accusation, no fabricated evidence, no editing of originals, no auto-resolving conflicts, no replacing an investigator's judgment, and — stated as its own principle, not just a restatement of the above — no scam/fraud/authenticity verdict of any kind. EvidenceX is an analyzer, not a detector. It never outputs "this is a scam" or "this document is forged." What it outputs is structured, sourced flags: missing details, structural inconsistencies, gaps against what an authentic instance of that evidence type normally contains, and contradictions across evidence — always for a human investigator to weigh, never a system-issued conclusion.

North-star differentiator: every fact on screen answers "where did this come from, and how confident are we?"

2. Primary User & Jobs-to-be-Done

Persona: Cybercrime investigator / fraud analyst (also usable by a bank fraud-ops team or an individual documenting a case for police).

Jobs:

  1. Dump all evidence for an incident in one place without losing anything.
  2. Get a first-pass structured read of "what happened, in what order" in minutes, not hours.
  3. Know which facts are solid, which are contradicted, and which are still missing — before writing a report.
  4. Produce a report that a senior officer / bank / court can trust because every claim is sourced.

Processing pipeline is strictly sequential per evidence item (upload → validate → hash → store original, immutable → OCR → normalize → extract → merge into case), and case-level analysis (timeline, conflicts, missing info, summary) re-runs incrementally every time new evidence lands, layer by layer, chronologically — never re-deriving facts from scratch in a way that could silently overwrite a prior source link.

5. Functional Requirements by Pipeline Stage

5.1 Ingestion

  • Accept: PNG/JPG/JPEG, PDF, TXT, CSV, pasted text, URL string, manual transaction form.
  • Validate MIME type + extension match, enforce max size (e.g. 15 MB/file), sanitize filenames, block path traversal.
  • Compute SHA-256 of the original file before any processing; store hash + immutable original; all downstream artifacts (OCR text, extracted JSON) reference the evidence ID, never replace it.
  • Assign EV-### ID at ingestion time, independent of processing outcome.

5.2 OCR / Text Extraction

  • Run OCR on images/scanned PDFs; run direct text extraction on text-layer PDFs/TXT/CSV.
  • Store raw OCR text + engine confidence per evidence item.
  • Failure mode: if OCR yields empty/low-confidence output, mark evidence OCR extraction unavailable — do not synthesize placeholder text.

5.3 AI Extraction (schema-locked, source-tagged)

Output strictly conforms to:

{
  "persons": [], "phone_numbers": [], "emails": [], "upi_ids": [],
  "bank_accounts": [], "transaction_ids": [], "transactions": [],
  "urls": [], "dates": [], "times": [], "locations": [],
  "messages": [], "other_entities": []
}

Every item carries value, source_evidence_id, confidence, evidence_reference (e.g. line/region). Status per field is one of FOUND / INFERRED / MISSING / CONFLICTING — never silently promoted to a "confirmed" fact if it was inferred.

No-hallucination rule (hard constraint): the model is prompted to extract only what is explicitly present; anything not present returns "Not Found"; anything ambiguous returns "Uncertain". This is enforced structurally (schema + explicit refusal instruction) and validated post-hoc by checking every extracted value appears as a substring/near-match in the source OCR text before it's accepted into the structured store — extractions that fail this check are downgraded to Uncertain rather than discarded silently, so the investigator can still see and verify them.

5.4 Transaction & Timestamp Extraction

  • Parse amounts, currency, sender/receiver, method, transaction ID, and any timestamp co-located with the transaction mention.
  • Normalize dates/times to a single canonical timezone for ordering, while preserving the original as-written string for traceability.

5.5 Timeline Generation

  • Merge all extracted timestamped events (messages, URL clicks, transactions, doc timestamps) into one chronological feed.
  • Events with no extractable timestamp are listed in an "unordered / needs manual placement" bucket rather than guessed into a slot.
  • Every node links back to its EV-###.

5.6 Conflict Detection

  • Compare same-field values across different evidence sources (e.g. transaction amount, sender name, phone number).
  • Flag as conflict when two sourced values for the same logical fact differ beyond a tolerance (e.g. exact match required for IDs; small formatting differences like ₹5,000 vs Rs. 5000 are normalized before comparing, so only genuine discrepancies surface).
  • Never auto-resolve; both values + both sources are shown side by side with a manual "reviewed / not reviewed" toggle for the investigator.

5.7 Missing-Information Detection

  • Configurable checklist (transaction ID, timestamp, amount, payment method, sender, recipient, contact number, URL, incident date, etc.).
  • A field is "missing" only if it is absent from every piece of evidence in the case, not just the current one being viewed.
  • Each missing item includes importance (HIGH/MEDIUM/LOW) and a suggested verification action (e.g. "Request bank statement for txn confirmation").

5.8 Traceability

  • Any fact rendered anywhere in the UI is clickable and opens a side panel showing: fact, source evidence, extracted location, confidence, and a jump-to-original-evidence action.
  • This is enforced as a shared UI component, not re-implemented per screen, so it can't be forgotten on a new page.

5.9 Privacy / Masking

  • Masking runs before storage of any display copy — not just at render time. The raw OCR/extracted text is retained internally for traceability and matching, but anything rendered in the UI, PDF, or JSON export passes through the masking layer first.
  • Sensitive fields are not all treated the same — reveal risk differs by field type:
Field class Default display Reveal available?
Phone, email, UPI ID, bank/account number Masked (98******10, ni***@gmail.com, ********8990) Yes — authorized "Reveal" action, logged (who/when)
Card numbers, full account numbers if pasted raw Masked, at most last 4 digits shown Yes — authorized reveal, logged
OTP / one-time codes Fully redacted (****), always No — never revealed, to anyone, at any authorization level. The one-time code has no investigative value once used or expired; only the event matters ("OTP requested at 10:35," "OTP shared with scammer at 10:42"), which is what's preserved and shown, not the digits
Passwords / PINs, if ever present in evidence text Fully redacted, always No — same as OTP
  • Every reveal action is logged (who revealed what, when) even in the MVP — this is exactly the kind of control a real investigation tool needs to demonstrate.
  • API keys and secrets never reach the frontend bundle or logs.

5.10 AI Summary & Final Report

  • Summary sections: executive summary, incident sequence, financial summary, key entities, missing information, conflicts, observations — each observation still carries a source reference where possible.
  • Report always ends with the fixed disclaimer: "The information presented is extracted from supplied evidence and requires investigator verification."
  • Export as PDF (formatted report) and JSON (full structured case, for handoff to other tooling).

5.11 Search

  • Global search across name, phone, email, transaction ID, UPI ID, URL, evidence ID, case ID.
  • Filters: date range, evidence type, conflict status, processing status.

6.1 Sequence-Completeness Flags Against Known Fraud-Script Structures

Sits in the pipeline after Timeline Generation, before AI Summary. Its job is narrower than it may first sound: it answers "against commonly-seen scam-script structures, which expected steps have supporting evidence and which don't" — it is a completeness check against known structures, the same category of capability as Section 6.5, applied specifically to multi-stage scam narratives. It does not classify a case as fraud, and it does not declare an outcome; it flags gaps and, where evidence allows, reports what the evidence itself supports (e.g. a matching debit record) as a sourced fact, not a conclusion.

Why this needs two different matching mechanisms, not one vector DB:

  • Transaction ↔ bank-statement reconciliation is structured data (amount, date, reference), matched via fuzzy structured join (amount tolerance + date-window + optional reference match) against records the extraction pipeline already produced — not a semantic-similarity problem, and forcing it into a vector DB would obscure why two records matched, which breaks traceability.
  • Scam-stage matching (e.g. "asking for OTP," "OTP shared," "urgency/threat language") genuinely needs semantic matching, because scripts are phrased differently every time. This is where embeddings/a vector store are appropriate.

Mechanism:

  1. Maintain a small library of known scam playbooks (OTP Phishing, Fake Bank Call, Investment Scam, Job Scam, etc.), each an ordered stage list: Initial Contact → Pretext/Impersonation → Credential/OTP Request → Compliance (shared) or Refusal → Transaction Attempted → Transaction Completed → Follow-up Ask.
  2. Each incoming message/evidence snippet is checked against every stage using two layers:
    • Deterministic keyword/pattern rules — works even in Demo Mode with no AI key (e.g. "share the OTP," "verify your account," a bare 4–6 digit code sent by the victim).
    • Semantic similarity against a small set of exemplar phrasings per stage, for language that doesn't hit exact keywords.
  3. Transaction confirmation runs as the separate structured-reconciliation step described above, linking chat-mentioned amounts to actual statement debits.
  4. Outcome classification is strictly evidence-gated, never inferred:
    • No compliance-stage evidence found → "Scam contact evidenced; no compliance evidence found."
    • Compliance evidence present, no matching debit found → "Compliance evidenced; financial loss not confirmed in supplied evidence."
    • Compliance evidence and a matching debit → "Financial loss confirmed — matches transaction record EV-###."
    • A stage with no evidence is reported as "No evidence found for this stage," never as proof the step didn't happen, and it also feeds the existing Missing Information list rather than being a separate silent gap.
  5. Every stage carries a confidence score and full source traceability, identical to every other fact in the system.

New UI element — "Fraud Pattern Match" card (on Case Overview and in the Final Report): matched playbook name, a per-stage evidenced/not-evidenced bar, and the financial-outcome line, closing with the same disclaimer used elsewhere: this is a pattern-match signal for investigator review, not a determination of fraud or completion.

Data model impact: add a fraud_pattern_matches table (case_id, playbook_name, stage, status [EVIDENCED/NOT_FOUND], source_evidence_id, confidence) and a reconciliations table (chat_transaction_ref, statement_evidence_id, match_confidence, match_basis) — both following the same source_evidence_id + confidence + extraction_status convention as the rest of the schema.

Edge cases specific to this stage:

Scenario Required behavior
Victim never shared OTP (refused) Compliance stage marked "No evidence found" — explicitly not labeled "fraud failed," since refusal evidence and absence-of-evidence must stay distinguishable
Bank statement shows a debit but no chat ever mentions an amount Reconciliation has nothing to link to; debit stands alone as an unlinked transaction, flagged for investigator attention rather than force-matched
Multiple similarly-timed debits, one matches the scam narrative Reconciliation must show all candidate matches with their confidence, not silently pick the top one
Message doesn't match any known playbook System shows "No known pattern matched" rather than forcing a best-fit label — avoids false-pattern bias
Same evidence could plausibly fit two playbooks (e.g. OTP phishing vs fake bank call) Show both matches with their respective confidences; do not auto-pick one

6.2 System Intelligence Architecture: Case Context, Entity Resolution, Cross-Case Learning

The AI calls are stateless — there is no memory between API requests. "Understanding a case" is therefore something the backend builds and hands back to the model on every call, not something the model retains on its own. This is deliberately RAG-style context assembly, not fine-tuning: cheaper, hackathon-appropriate, and — critically — auditable, since every piece of context fed back in is itself a traceable fact.

a) Entity Resolution (case entity graph)

  • Extraction happens per-evidence-item, but the same person/number/handle often appears differently across sources ("Rahul," "the bank executive," "+91 98xxx," "unknown caller").
  • A resolution step runs after each extraction: new mentions are matched against existing canonical entities in the case (via exact match on structured identifiers like phone/UPI/account, plus fuzzy/semantic match on names), and either merged into an existing entity as a new alias or created as a new canonical entity.
  • Each canonical entity keeps a list of all raw mentions, each mention still pointing at its original EV-### — resolution never deletes or hides the raw mention, it just organizes them under one identity.
  • This directly fixes a real bug class: without it, "sender name missing" could be wrongly flagged on evidence where the sender was already identified elsewhere in the case.

b) Case Context Object (how the system stays case-aware)

  • After every evidence item is processed, the backend updates a compact structured snapshot of "what this case currently knows": canonical entities, confirmed timeline events, current scam-pattern stage hits, open conflicts, open missing-info items — all as retrieved facts with source IDs, never as the model's own prior free-text opinions.
  • This snapshot is included in the prompt context for every subsequent extraction, conflict-check, stage-detection, and summary call for that case only. So evidence #5 is interpreted with knowledge of what evidence #1–4 already established (e.g. recognizing a repeated phone number as the same entity, or recognizing an OTP-sharing message as the compliance stage because the pretext stage was already confirmed earlier in the same case).
  • Because the object is rebuilt per-case from that case's own evidence, two cases never bleed into each other unless the cross-case layer below is explicitly used — each case genuinely gets its own "understanding," not a shared one.
  • Since context is always sourced facts, a later call cannot hallucinate forward from an earlier hallucination — every element of the context is itself checkable against an EV-###.

c) Cross-Case Indicator Layer (opt-in, privacy-scoped)

  • A separate, minimal index storing only indicators already flagged in any case — phone numbers, UPI IDs, bank accounts, URLs/domains — never full case narratives or victim details.
  • New cases are checked against this index for exact-match hits ("this UPI ID appears in 2 other cases") and, using embeddings, for semantic similarity between the new case's scam messages and previously-seen scam-script exemplars.
  • This is the one place a vector store earns its role in this system — matching scam language across cases, not matching case content or resolving within one case.
  • Cross-case hits are surfaced as a signal ("seen elsewhere in the system") with access to full details of the other case gated separately — this is a system that connects dots, not one that leaks one victim's case into another's view.

New edge cases from this architecture:

Scenario Required behavior
Two different real people happen to share a common first name in the same case Entity resolution must not merge on name alone — require a corroborating identifier (phone/UPI/account) or leave as separate entities with a "possible match" flag for investigator confirmation, never a silent auto-merge
Case context snapshot grows very large (many evidence items) Summarize/compress the snapshot passed into each prompt (e.g. canonical entities + open items only, not the full raw text of every prior evidence item) to control cost and stay within context limits
Cross-case indicator match on a very common value (e.g. a generic customer-care number) Require a minimum specificity/frequency threshold before surfacing a "seen elsewhere" signal, to avoid false pattern-matching on noise
Investigator corrects an entity merge (splits two wrongly-merged entities) Correction is stored and respected for all future processing in that case; original mentions and sources remain untouched

6.3 Additional Hardening (from real-world gaps)

  • Evidence authenticity vs. integrity: SHA-256 hashing proves a file wasn't altered after upload — it says nothing about tampering before upload (e.g. a doctored transfer-confirmation screenshot, a common real tactic). Add a lightweight authenticity-signal check (image metadata/EXIF inspection, basic visual-inconsistency heuristics) explicitly labeled as "signal, not proof" in the UI, never as a fraud/authenticity verdict.
  • Language scope, stated explicitly: Indian fraud chats are frequently Hinglish or regional-language, sometimes in Latin script. State the MVP's actual support boundary (e.g. English + basic Hindi transliteration) rather than silently failing or mis-extracting on unsupported text; unrecognized-language content is marked "extraction limited," not dropped.
  • Chain-of-custody export: alongside the narrative PDF report, provide a separate, minimal hash manifest export (every evidence file, its SHA-256, upload timestamp) — the artifact that actually matters if the case is handed to law enforcement.
  • Cost/rate control: cache extraction results by evidence hash so a re-uploaded duplicate never triggers a re-processing API call; batch or queue processing for large cases rather than firing unbounded parallel calls.

6.4 Innovation: Scammer Signature Fingerprinting ("Have We Seen This Before?")

This extends the Cross-Case Indicator Layer (6.2c) from "did this exact phone number appear before" into recognizing a scammer's operating pattern, even when the phone number, UPI ID, or wording is slightly different — the same real-world capability fraud units want: "this looks like the same operation we saw last month."

Important framing constraint, kept consistent with the rest of the product: the system never "declares a scam." What it does is surface a high-confidence pattern-match alert for investigator review — attribution to the same individual is not claimed, since scam scripts/templates are frequently shared or resold across many different operators. The system matches operations/scripts, not identities.

What gets fingerprinted, once a case's kill-chain stages (Section 6.1) are detected:

  • Exact indicators: phone numbers, UPI IDs, bank accounts, URLs/domains used in the scam.
  • Behavioral signature: an embedding generated from the structure and phrasing of the message sequence — stage order, pretext style, urgency-language patterns, template phrasing — the same vector mechanism already used for stage detection in 6.1, reused here at the whole-sequence level instead of per-message.
  • Together these form a Scammer Operation Profile: a bundle of known indicators + a behavioral signature + a running count of how many cases have matched it, stored separately from any victim's case narrative (same privacy boundary as 6.2c).

Matching flow for new evidence:

  1. As soon as a new case's evidence sequence produces a behavioral signature, it's compared against stored profiles via vector similarity, and its extracted indicators are checked for exact overlap.
  2. Confidence is weighted higher when both layers agree (same UPI/phone and similar script) than when only one does (similar script, different number — likely a shared template, not necessarily the same actor).
  3. A match above threshold surfaces immediately as a "Known Pattern Match" alert on Case Overview: profile ID, number of prior cases matched, matched indicators, script-similarity score, and a direct link to review (not copy) the prior cases' pattern data — never their victim details.
  4. Alert wording is deliberately careful: "This case matches a known scam operation profile (seen in 4 prior cases) with 91% pattern confidence — review recommended." Never "this is a scam" or "this is the same person."

Profile lifecycle & safeguards (this is where most systems like this go wrong):

  • A profile is only created/updated from a case after an investigator has reviewed and confirmed the kill-chain findings for that case — this prevents a single bad extraction from poisoning the shared fingerprint database.
  • Profiles accumulate confidence with more confirmed matches; a first-time signature is stored as "unconfirmed/new" and doesn't yet trigger alerts on its own.
  • If two previously-separate profiles later turn out to share strong indicator overlap, they're flagged for investigator-approved merge — never auto-merged silently.
  • A generic/very common script (e.g. a mass-market phishing template used by many unrelated actors) is expected to produce broad, lower-confidence matches — the profile record explicitly tracks match count and average confidence so a "used by everyone" template doesn't masquerade as a tight, specific match.

New edge cases:

Scenario Required behavior
Same script/template used by many unrelated scammers (a shared "kit") Profile shows high case-count but should surface as "common template pattern," not "same operation," once case-count crosses a configurable breadth threshold
Scammer slightly varies wording each time (evasion) Behavioral signature is similarity-based, not exact-match, so minor rewording still matches — but confidence scales with actual similarity, not a hard yes/no
Two unrelated cases share one coincidental indicator (e.g. reused/recycled phone number, not fraud-related) Weighting requires behavioral similarity and indicator overlap to reach high confidence; indicator-only overlap alone stays flagged as low-confidence
Investigator disputes a fingerprint match as wrong Match can be dismissed per-case with a reason; dismissed matches don't feed back into the profile's confidence
New case's own kill-chain stages are incomplete (e.g. only 2 of 5 stages evidenced) Fingerprint is generated and matched against existing profiles, but flagged "generated from partial sequence" — lower confidence banner

Data model addition: scammer_profiles (profile_id, behavioral_signature_vector, indicator_list, confirmed_case_count, avg_confidence, status [new/confirmed/common-template]) and profile_matches (case_id, profile_id, match_confidence, matched_basis [indicator/behavioral/both], investigator_reviewed boolean).

6.5 Core Engine: Structural Completeness & Expected-Field Analysis (Analyzer, Not Detector)

This is the correct center of the product, and it must stay the framing for everything else in this document: EvidenceX does not decide whether something is a scam. It reasons about what a genuine instance of a given evidence type normally contains, compares the supplied evidence against that expectation, and raises structured, chronological flags for whatever is missing or inconsistent. The investigator draws the conclusion; the system draws attention to gaps.

This generalizes across two levels of evidence, both handled by the same underlying mechanism:

a) Single-document structural analysis

  • Maintain a library of expected-structure templates per evidence type — not rigid OCR templates, but a reasoning-guided checklist of what a genuine instance of that type typically includes. Examples:
    • Bank statement: account holder name, IFSC/branch identifier, statement period, opening/closing balance, consistent running-balance arithmetic, transaction reference numbers, consistent narration formatting, bank letterhead/footer elements.
    • UPI/payment screenshot: transaction ID (UTR/RRN), timestamp, payer/payee VPA, status indicator, app-consistent UI layout.
    • Email: sender domain, header consistency, reply-chain structure where claimed.
    • Chat/message screenshot: consistent timestamp progression, consistent sender identity/UI element placement across the same claimed conversation thread.
  • For each uploaded item, the system checks which expected elements are present, missing, or structurally inconsistent (e.g. a running balance that doesn't arithmetically follow from the listed transactions; a UPI screenshot with no transaction ID at all) — every check produces a flag with a plain-language rationale, tied to the evidence ID, never a "forged/genuine" label.

b) Evidence-sequence (array) structural analysis

  • The same principle applied to a set of related evidence — e.g. the 5-screenshot scam sequence described earlier. Rather than matching against a "scam playbook" to infer intent, the system checks the sequence for structural completeness of the narrative being presented: is there a coherent step order, are there gaps where a claimed step (e.g. "victim received confirmation SMS") has no corresponding evidence, are timestamps consistent with the claimed sequence.
  • Output is the same kind of flag as the single-document case: "Step 3 of the sequence (payment confirmation) has no supporting evidence" or "Screenshots 2 and 4 show inconsistent timestamp formatting for the same claimed conversation." This is presented as a gap in the evidence, not a statement about what did or didn't happen.

c) "Thinking capability," precisely defined

  • This is where the system needs to go beyond fixed-schema extraction: the AI step is prompted to reason about a given evidence item using general domain knowledge of what that document/evidence type normally looks like, rather than only filling predefined fields. It should be able to notice something like "this bank statement's transaction narration format changes style halfway through the document" even if "narration format consistency" wasn't an explicitly hardcoded field to check.
  • To keep this auditable rather than a black box: the reasoning step must output its specific observation + which expected element it relates to + a plain-language rationale, in the same source-tagged structure as every other fact in the system — free-form "gut feeling" flags without a stated basis are not acceptable output.
  • This reasoning layer sits alongside the deterministic checklist in (a)/(b), not instead of it — deterministic checks catch the reliable, demo-safe cases (works in Demo Mode too, via a rule-based template checklist); the reasoning layer catches the subtler, type-specific inconsistencies that a fixed schema would miss.

Output surface: a new "Structural Flags" panel per evidence item and per evidence sequence, each flag showing: what's missing/inconsistent, why it's expected for that evidence type, confidence, and the evidence ID(s) involved. These flags feed into the existing Missing Information (5.7) and AI Summary views alongside the case-level missing-fact flags, clearly labeled as document/sequence-structure flags so they're never confused with case-fact flags.

Edge cases:

Scenario Required behavior
Evidence type doesn't match any known template (e.g. an uncommon regional bank's statement format) Fall back to general-reasoning mode only, flagged as "no reference template for this format — limited structural check," rather than forcing a mismatch against the wrong template
A genuine document simply uses an unusual but legitimate format (e.g. a small local bank's statement layout) Flags are worded as "deviates from common format" or "element not found," never "inconsistent with genuine documents," to avoid false implication
Partial/cropped screenshot Missing elements outside the cropped region are flagged as "not visible in supplied evidence," distinct from "absent from the document"
Reasoning layer produces a flag with no clear basis Rejected before display — every flag requires a stated expected-element reference; unanchored observations are dropped, not shown as speculation
Sequence has extra, unclaimed evidence beyond the narrative being checked Extra evidence is retained and shown, not treated as an error — the check only evaluates completeness of the claimed sequence, not whether more evidence exists

7. Non-Functional Requirements

  • Reliability: a single failed extraction never crashes the case view; errors are isolated per evidence item.
  • Explainability: every AI-derived value shows confidence and provenance.
  • Security (MVP-scoped): file validation, size limits, filename sanitization, path-traversal protection, parameterized queries, env-based secrets, no keys in frontend, SHA-256 hashing of originals. Documented as MVP-level, not production-hardened (no encryption-at-rest, no RBAC beyond a single demo login, no audit-grade access logs).
  • Accessibility: keyboard-navigable, labeled controls, adequate contrast in the dark theme, responsive down to tablet width.
  • Performance target for demo: end-to-end (upload → summary) under ~30 seconds for the bundled demo case.

8. Data Model (core entities)

cases → evidence → evidence_text (OCR/raw text) → entities, transactions, timeline_events (each FK to evidence) → conflicts (FK to two evidence/fact pairs) → missing_information (FK to case) → reports (FK to case, generated snapshot).

Every child table carries source_evidence_id, confidence, and extraction_status (FOUND / INFERRED / MISSING / CONFLICTING) so traceability is a first-class column, not a UI afterthought.

Added for the intelligence layer (Section 6.2):

  • case_entities (canonical entity per case) + entity_mentions (raw mentions, each FK to source_evidence_id, FK to case_entities) — the alias/resolution graph.
  • case_context_snapshots (case_id, version, compact JSON of current entities/timeline/open conflicts/open missing-info, updated after each evidence item) — what gets fed back into subsequent AI calls.
  • cross_case_indicators (indicator_value, indicator_type [phone/UPI/account/URL], case_id, source_evidence_id) — the minimal opt-in index behind the "seen elsewhere in the system" signal, deliberately excluding narrative/victim content.

9. Suggested Tech Stack

  • Frontend: Next.js + React + TypeScript + Tailwind (dark, professional theme).
  • Backend: FastAPI (Python), SQLAlchemy ORM, PostgreSQL.
  • AI: provider-agnostic abstraction layer (Gemini/OpenAI interchangeable) + a Demo Mode extractor that mimics the same interface with deterministic mock output.
  • OCR: Tesseract (or cloud OCR fallback if configured).
  • PDF report: server-side PDF generation (e.g. WeasyPrint/ReportLab).
  • Storage: local disk for MVP, structured behind a storage interface so S3/GCS can be swapped in later.

10. Success Criteria

An evaluator can, without manually editing extracted data: create a case → upload evidence → watch it process → see extracted entities and transactions with sources → see a chronological timeline → see at least one flagged conflict and one missing field → read an AI summary → generate a sourced PDF/JSON report. Full flow demoable in 3–5 minutes via a one-click "Load Demo Case."
